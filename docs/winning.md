# 토요일 당첨 확인

설정일: 2026년 10월 9일, 한국시간.

## 이전 배경

`lotoManager`의 당첨 확인(토 21:50 KST)은 개인 서버의 구매 기록을 읽은 뒤 공개 당첨번호 API로 회차별 번호를 조회해 서버에 저장했다. 2026년 10월 3일 실행은 10분 간격 5회 재시도 후에도 당첨번호를 확인하지 못했다. 해당 워크플로는 `disabled_manually` 상태로 유지한다.

이 저장소는 개인 서버 대신 커밋된 [`records/purchases.csv`](../records/purchases.csv)를 구매 기록으로 사용하고, 공개 당첨번호 API(`/lt645/selectPstLt645Info.do`)와 대조해 등수를 직접 계산한다. 동행복권 로그인과 계정 Secrets는 사용하지 않는다.

## 워크플로

- 파일: `.github/workflows/check-winning.yml`, `Check Lotto Winning (Saturday)`.
- 예약: 토 21:30 KST(`30 12 * * 6` UTC), 보조 확인 일 09:00 KST(`0 0 * * 0` UTC). 이미 기록된 회차는 조회·알림 없이 건너뛴다.
- 회차: 2026년 10월 10일 1245회를 기준으로 가장 최근 토요일 20:45 KST 이후 추첨 회차를 계산한다. 수동 실행 시 회차를 지정할 수 있다.
- 미발표 시 ⏳ 알림을 보내고 아무것도 기록하지 않는다. 다음 예약에서 다시 확인한다.

```bash
python3 -m monitor check                     # 최근 회차, 터미널 출력만
python3 -m monitor check --round 1246 --save # records/에 기록
```

## 등수 계산

| 일치 | 등수 |
| --- | --- |
| 6개 | 1등 |
| 5개 + 보너스 | 2등 |
| 5개 | 3등 |
| 4개 | 4등 (50,000원) |
| 3개 | 5등 (5,000원) |

1~3등 금액은 해당 회차 API의 1인당 당첨금(`rnk{n}WnAmt`)을 사용한다. 실제 수령액(세금 등)과 다를 수 있으며, 공식 당첨 여부는 동행복권 구매 내역에서 확인한다.

## 기록

| 파일 | 내용 |
| --- | --- |
| `records/draws.csv` | 회차, 추첨일, 당첨번호, 보너스, 1~5등 1인당 당첨금 |
| `records/winnings.csv` | 회차, 슬롯, 방식, 번호, 일치 개수, 등수, 당첨금 |

구매 기록이 없는 회차도 당첨번호는 `draws.csv`에 남긴다. 잔액·계정 정보는 기록하지 않는다.

## 검증 상태

모의 응답으로 회차 계산, 1~5등 판정(2등 보너스 포함), 미발표·형식 오류, 중복 기록 방지를 테스트했다.

2026년 10월 9일 [수동 실행](https://github.com/k-ubella/lotto-monitor/actions/runs/37908799565)으로 1244회를 기록 없이 확인했다. GitHub Actions에서 공개 당첨번호 API 조회와 응답 해석(`draw_checked`), Discord 전송·재조회(`message_verified`)가 성공했다. 첫 실행은 `records/` 폴더가 없어 커밋 단계가 실패했고, 폴더를 만든 뒤 `git add`하도록 고쳤다. 예약 실행과 실제 구매 기록 대조·커밋은 아직 확인하지 않았다.
