# 같은 Discord 채널에 들어온 알림, 어느 GitHub Actions에서 보낸 걸까?

두 개의 GitHub 저장소가 같은 Discord 채널로 알림을 보내고 있었다. 한쪽에서는 오류가 반복됐지만 다른 쪽에서는 정상 알림이 들어왔다. 알림만 보고 같은 프로그램이 때로는 성공하고 때로는 실패한다고 생각했다.

문제를 이해하려면 알림을 보낸 저장소와 실행을 먼저 구분해야 했다. 이 글은 실제 확인한 실행 기록을 바탕으로 정리한 GitHub Actions 진단 사례다. 새로운 공개 프로젝트의 대상으로는 조회·알림·기록 기능만 검토한다.

## 1. 코드에 적힌 일정과 알림의 시각을 구분하기

처음 기억했던 운영 일정은 토요일 작업과 월요일 잔액 조회였다. 그러나 `lotoManager`에서는 2026년 9월 27일 커밋으로 작업 일정이 바뀌어 있었다.

| 저장소 | 변경 또는 확인한 상태 |
| --- | --- |
| `lotoManager` | 9월 27일 `d463bea`에서 기존 토요일 작업을 평일 작업으로, 월요일 잔액 조회를 토요일 조회로 변경 |
| `vibe-lotto` | 토요일 작업과 월요일 잔액 조회 일정 유지 |

예약 시각은 실제 시작 시각과 같지 않을 수 있다. GitHub Actions의 예약 작업은 지연될 수 있으므로, Discord 메시지의 시각을 예약 설정과 바로 비교하지 않고 실행 기록의 시작 시각과 비교해야 한다. GitHub API의 UTC 시각도 한국시간으로 변환해서 비교했다.

## 2. 같은 문구와 같은 실행 시각으로 발신 저장소 찾기

결정적인 단서는 알림 문구였다. `vibe-lotto`의 `notification.py`에 다음 문구가 있었다.

> 월요일 잔액 체크 완료: 현재 잔액 …

이 문구는 `lotoManager`의 현재 잔액 조회 코드와 해당 파일의 커밋 이력에서 찾을 수 없었다. 실행 기록도 대조했다.

| 관찰한 알림 | 실행 기록과 대조한 결과, 한국시간 |
| --- | --- |
| 2026년 10월 5일 12:30 월요일 잔액 알림 | `vibe-lotto`의 `Check Balance`가 12:30:32에 시작 |
| 2026년 10월 3일 11:23 작업 완료 알림 | `vibe-lotto`의 토요일 작업이 11:23:12에 시작 |

문구와 시각이 함께 일치하므로 이 알림은 `vibe-lotto`의 실행에서 나온 것으로 판단할 수 있었다. 두 저장소가 정확히 같은 웹훅 URL을 쓰는지까지는 확인하지 않았다. 같은 채널에 알림이 들어온다는 관찰과 웹훅 값이 동일하다는 주장은 구분해야 한다.

앞으로는 알림에 저장소 이름, 워크플로 이름, 실행 링크를 포함하면 출처를 바로 확인할 수 있다. 민감한 계정 정보나 웹훅 주소를 넣을 필요는 없다.

## 3. GitHub API의 Forbidden과 GitHub 권한 오류 구분하기

처음에는 GitHub API 실행 기록 조회가 `Forbidden`으로 실패했다. 확인 결과 `github.com` 접속과 Git 저장소 읽기는 성공했지만 `api.github.com`은 프록시의 `CONNECT` 단계에서 403으로 차단됐다.

이는 요청이 GitHub API에 도달하기 전 발생한 네트워크 정책 차단이었다. API 계정 권한 오류로 단정하거나 새 토큰부터 발급할 상황이 아니었다.

환경의 허용 도메인에 `api.github.com`을 추가하고 적용한 뒤 실행 기록 조회가 성공했다. 저장소 복제 권한, GitHub API 접근, 워크플로 실행 권한은 각각 확인해야 한다.

## 4. 초록색 Actions가 실제 기능 성공을 보장하지 않는 이유

최근 실행 기록에는 `success`가 표시돼 있었다. 하지만 스크립트가 예외를 잡아 오류 알림을 보내고 정상 종료하면 GitHub Actions는 해당 명령이 성공한 것으로 판단할 수 있다.

잔액 조회만 실행하는 `Manual Balance Check` 워크플로를 따로 추가했다. 원래 스크립트의 종료 상태를 보존하고, 현재 스크립트가 출력하는 오류 문구가 있으면 테스트 단계가 실패하도록 구성했다.

이 방식은 기존 코드를 점검하기 위한 임시 호환 방식이다. 새로운 프로젝트에서는 결과를 구조화하고 실패할 때 명시적으로 0이 아닌 종료 코드를 반환하는 설계가 더 적절하다. 로그 문구가 바뀌면 문자열 기반 판정도 함께 변경해야 한다.

## 5. 서버 저장 제거 후에도 남은 잔액 조회 오류

잔액 조회 코드에는 조회 결과를 개인 서버에 저장하는 단계와 주간 기록을 읽는 단계가 추가돼 있었다. 이 단계들이 조회와 같은 예외 처리 블록 안에 있어 부가 기능 실패가 전체 조회 실패처럼 보일 수 있었다.

우선 서버에 잔액을 저장하는 단계만 제거했다. 외부 통신을 모의한 검증에서 잔액 조회, 주간 기록 읽기, 알림 전송이 유지되는 것을 확인했다. 실제 구매를 수행하는 코드는 수정하거나 테스트하지 않았다.

이후 잔액 전용 Actions 테스트에서는 다음 오류가 확인됐다.

```text
'NoneType' object has no attribute 'get_text'
```

현재 코드가 `.total_new strong` 요소를 찾지 못한 상태에서 `.get_text()`를 호출한 것이다. 오류 알림의 Discord 전송은 성공했고, 새 테스트 워크플로는 이를 실패로 표시했다.

이 오류는 서버 저장 이전의 페이지 분석 단계에서 발생했다. 다만 요소가 없는 이유는 아직 확정되지 않았다. 로그인 실패, 로그인 페이지로의 이동, 서비스 오류 응답, HTML 구조 변경 등이 구분되지 않은 상태다.

또한 현재 로그인 판정은 특정 비밀번호 오류 문구가 없으면 성공을 출력한다. 로그의 “로그인 성공”만으로 인증 성공을 보장할 수 없다.

수정하려면 먼저 응답 상태와 이동한 페이지를 확인하고, 인증 성공을 검증한 뒤 실제 정상 페이지에서 잔액 요소를 확인해야 한다. 응답 HTML에는 계정 정보가 들어갈 수 있으므로 그대로 공개 로그나 블로그에 붙이지 않는다. 선택자만 임의로 바꾸거나 조회 실패를 0원으로 치환하면 문제를 숨길 수 있다.

## 6. 기존 자동 실행 중단

2026년 10월 9일 점검 시 다음 예약 워크플로를 GitHub에서 비활성화했다.

| 저장소 | 워크플로 | 확인 상태 |
| --- | --- | --- |
| `lotoManager` | `Automatic Lotto Buyer` | `disabled_manually` |
| `vibe-lotto` | `Buy lotto` | `disabled_manually` |
| `vibe-lotto` | `Check Balance` | `disabled_manually` |

두 저장소에 실행 중이거나 대기 중인 작업이 없는 것도 확인했다. `lotoManager`의 `Manual Balance Check`는 수동 전용으로 유지했다.

워크플로 파일은 삭제하지 않았다. 따라서 코드와 실행 이력은 남아 있으며, GitHub에서 다시 활성화할 수 있다. 워크플로 비활성화는 별도 서버의 예약 작업까지 중단하는 기능은 아니다.

## 7. 공개 저장소는 검토한 파일만 새로 구성하기

기존 비공개 저장소를 통째로 공개하는 방식에는 문제가 있었다. 한 저장소에는 `.history/.env_*`가 추적돼 있었고 다른 저장소에는 코드에 계정 정보가 직접 들어간 파일이 있었다.

새 공개 저장소는 구매 기능을 제외한 조회·알림·기록 기능으로 범위를 제한하고, 필요한 파일만 옮겨 새 Git 이력으로 구성하는 안을 준비했다. `.env`, `.history`, 암호화 키, 계정 데이터, 실제 응답, 실행 로그는 공개 대상에서 제외한다.

인증 정보가 과거 파일에 있었다면 파일 삭제만으로 기존 이력에서 제거되지 않는다. 이미 노출됐거나 외부와 공유한 값은 교체해야 한다. 블로그 스크린샷에서도 계정, 잔액, 구매 내역, 웹훅 주소 등 공개하지 않을 정보를 가려야 한다.

개발 검증은 비식별 테스트 데이터와 모의 HTTP 응답으로 시작하고, 외부 서비스 연동은 명시적으로 설정한 경우에만 실행하도록 구성한다. 공개 예제에 실제 자격 증명이나 개인 서버 주소를 넣지 않는다.

## 이번 점검에서 확인한 범위

알림의 출처, 일정 변경 커밋, API 네트워크 차단 원인, 잔액 전용 테스트 오류, 예약 워크플로 비활성화는 확인했다. 잔액 요소가 사라진 근본 원인과 새로운 공개 프로젝트의 실서비스 조회 성공은 아직 검증하지 않았다.

이 글은 공개 저장소에 포함된 블로그 게시용 초안이다. 외부 블로그에는 아직 게시하지 않았다. 새 공개 저장소는 문서로 시작했고, 이후 모의 JSON을 이용한 잔액 결과 표시·알림 문구 생성·로컬 기록 조회 예제를 추가했다. 성공·미확인·실패를 구분하고 실패를 0원으로 표시하지 않으며, 실패 종료 코드를 검증한다. 실제 서비스 조회 코드는 아직 포함하지 않는다. 선별 기준과 검증 범위는 [코드 검토 기록](code-review.md)에 정리했다.
